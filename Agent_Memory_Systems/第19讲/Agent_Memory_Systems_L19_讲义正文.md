# 第19讲｜图记忆、知识图谱与时间图谱

《智能体记忆系统：从零基础到科研理解》 · 第19/32讲 · 第四部分：记忆的表示、存储架构与检索机制

**副标题：怎样保存实体、关系和不断变化的历史？**

**本讲的核心问题：** 智能体可能清楚地保存了三句话，却不知道它们说的是同一项研究、指向同一次故障，或者涉及已经失效的旧决定。如何让智能体把分散的经历联系起来？它如何查询“谁决定了什么”“某项结论由哪些证据支持”“上个月有效、今天却已经撤销的限制是什么”？图结构能帮忙，但又不能解决什么？

**阅读约定：** 本讲为**纯理论课程**，不安排代码、系统安装和实验。D01、D07等所有项目时间线、权限情景、节点数量与计算结果都是**教学虚构**，不是我方真实实验、决策或性能评测。具体研究机制会标注代表性原文，并在文末给出可核查链接。

## 学习目标与完整主线

学完应当能够：①从普通语句画出节点和有类型的关系边；②区分RDF三元组、属性图、图数据库、知识图谱和Agent图记忆；③独立推演实体消歧与多跳查询；④解释事实有效时间与系统获知时间的不同；⑤理解来源链、冲突更新、时间图和混合检索的责任；⑥比较GraphRAG、HippoRAG、Zep/Graphiti；⑦解释何时简单文本/向量记忆已经足够；⑧从一条错误回答定位可能出错的环节。

[[FIG01]]

> **本讲核心原则：** 图可以显式保存“谁与谁有什么关系”，时间图可以保存“这条关系何时成立”，来源链可以保存“系统为什么会这样认为”。但**一条图边既不是客观真理，也不是行动授权**；关系是否真实、当前是否有效、是否足以支持行动，仍需要独立核验。

## 一、先从一个科研助手遇到的困难讲起

想象一个AI科研助手已经协助某课题30天。假设有以下**教学事件**：

- **D01**：研究者确定项目P以“离线梳理智能体记忆机制”为当前目标。
- **D03**：AI建议未来购买API额度扩大实验。这是**提议**，不是获批事项。
- **D07**：研究者允许“仅零费用离线检查”，明确不批准新的付费调用。
- **D11**：某个工具返回HTTP 504，日志表明一次访问失败，但原因尚未确认。
- **D18**：完成网络日志检查后，团队形成“本次504更可能源自网关超时”的**有证据但有范围的判断**。
- **D20**：研究者再次明确“未经新的批准不得恢复付费API请求”。
- **D30**：研究者问：“当时为什么暂停，哪些证据支持判断，现在允许恢复什么？”

如果记忆只有一组互不关联的段落，系统就可能找到“API”“超时”“研究方向”三个相似片段，却无法明确：哪句话是AI建议？哪句话是用户决定？哪个日志和哪个故障事件对应？哪一个版本仍有效？**这些恰好就是关系问题和时间问题。**

[[FIG02]]

### 1.1 图不是为了把所有文字改成小圆点

存储历史原文仍然很重要。图的作用是**把原文中的可复用关系显式表示出来，作为检索和推理的索引或视图**。好的设计通常同时保留原始事件、抽取后的事实、图的来源引用和当前状态。否则抽取过程漏掉一句“尚未批准”，即使关系图十分漂亮，也只是在系统化地保存错误。

### 1.2 图最擅长回答哪类问题？

问题A：“HTTP 504出现在哪里？”——关键词搜索可能最直接。问题B：“关于停止付费的原话是什么？”——原始事件加时间过滤往往最可靠。问题C：“哪个决定限制了哪个计划，后续有没有覆盖它的决定？”——**跨实体、跨事件、跨时间的关系查询**更适合图式表达。问题D：“研究档案中有哪些主要主题？”——社区结构与摘要可能有帮助，但不需要默认认为复杂图优于强简单基线。

## 二、图结构的三个基础零件：节点、边和属性

数学上的图通常写作 `G=(V,E)`：`V`是**节点集合**，`E`是**边集合**。节点可以代表人、项目、实验、论文、工具、决策或事件；边表示节点之间的某种联系，例如“负责人属于项目”“决定限制行动”“日志支持故障诊断”。有向图的箭头有方向：A“提出”B与B“提出”A并不相同。

### 2.1 三元组：从一句话到一个关系

自然语言：“研究者负责项目P。”

可以抽象成：`(研究者, 负责, 项目P)`。这就是常说的 **主语—谓语—宾语**（Subject–Predicate–Object）三元组。其中“负责”不是一条自由描述，而是明确的**关系类型**。再加入`(项目P, 采用, 离线核查)`、`(决定D20, 限制, 付费调用)`，便可把原本散落的句子串起来。

[[FIG03]]

这里必须分清：**三元组表达一条主张，并不会自动使主张成为事实。** 如果它来源于AI自己的未核验摘要，应标成“AI提取的候选关系”，不能悄悄升级为“负责人正式决定”。

### 2.2 节点不仅可以是“人和物”，也可以是“事件或主张”

初学者容易把“研究者”和“项目P”画成节点，把“批准”画成边，随后发现批准还需要携带“批准范围、金额上限、时间、来源”。一个稳妥办法是将**批准事件或决定本身建成节点**，让它有身份与可追溯元数据：`(研究者, 作出, 决定D07)`、`(决定D07, 允许, 离线核查)`、`(决定D07, 不包含, 付费API调用)`。这个例子说明：什么应做节点、什么应做边，并不存在唯一答案，取决于查询需求与维护成本。

### 2.3 “邻居”和“路径”

如果项目P与决定D07相连，D07又与操作“离线核查”相连，那么从项目P到离线核查存在一条**两跳路径**。一跳是通过一条边；两跳是连续经过两条边。图中的路径能够表达多条分散记录之间的关联，但**有路径只表示“可以在结构上连接”，并不自动证明因果关系或逻辑蕴含**。

## 三、知识图谱、属性图和图数据库，究竟是什么关系？

**知识图谱（Knowledge Graph, KG）**重在用机器可处理的结构表达实体及其语义关系。**图数据库（Graph Database）**重在高效地保存、更新与查询图结构，是可能采用的实现技术之一。**图记忆系统（Graph-based Agent Memory）**还需要完整的记忆形成、状态维护、检索、来源核验与行动反馈过程。三者具有交集，但不是同义词。

### 3.1 RDF图：规范化三元组模型

W3C的RDF（Resource Description Framework，资源描述框架）采用主语、谓语、宾语三元组；标识符常用IRI，宾语也可以是字面量等，具体有类型约束。RDF可以方便跨来源链接知识。**RDF三元组本身不提供“来源”“置信度”“有效期”这些固定额外槽位**；要表达这些信息，需使用具名图、声明实体、RDF-star等相应建模方案，不能假定三元组天然已经解决追溯问题。[1]

### 3.2 属性图：节点和关系也可以携带属性

属性图（Property Graph）通常允许节点和边携带键值属性。比如`研究者 —[作出 {recorded_at:D07, source:E07}]→ 决定D07`。图中保存关系，属性中保存时间和来源；同一实体可以有多个标签、属性。这是一种直观工程模型，但**属性图的数据结构不能直接替代来源真实性和权限验证**。

[[FIG04]]

### 3.3 并不是必须购买专门的图数据库

小型项目完全可以在关系数据库中使用“节点表+边表”，用自连接或递归查询检索路径。也可以在文档数据库中保存嵌套关系，或在向量数据库的元数据里保存部分边。专门图数据库在高频邻接遍历、复杂路径查询中可能更方便，但图模型**属于逻辑表示**，图数据库**属于存储引擎选择**。这和第17讲“结构化对象不等于JSON数据库”的边界相同。

| 概念 | 主要解决什么 | 容易误解什么 |
|---|---|---|
| 图 / 节点边模型 | 显式表示联系和路径 | 有边就代表真实因果 |
| 知识图谱 | 组织具有语义的实体与主张 | 自动完成事实核查 |
| 属性图 / RDF | 表达结构与语义的不同体系 | 二者所有细节等价 |
| 图数据库 | 保存和高效查询图结构 | 使用图数据库才算有图记忆 |
| Agent图记忆 | 持续写入、更新、检索、使用 | 画出图就拥有长期智能 |

## 四、关系是怎么从自然语言中“长出来”的？

一条用户消息原本是字符串。要把它转成图，系统一般会经过若干逻辑环节：**接收事件→识别实体→识别关系→实体消歧→补充限定信息→与已有图比较→写入当前关系/历史版本→建立检索入口**。在真实实现中，顺序与组件可能不同，但每个责任点都值得独立理解。

[[FIG05]]

### 4.1 第一步：识别实体（Entity Extraction）

“第11天，评分脚本V2在项目P的T07任务上超时。”系统需要从句子中识别：项目P、评分脚本V2、T07任务、超时事件E11。实体不只是专有名词，也可能是一个稳定的事件ID。名称“评分器”“评估脚本”和“V2脚本”可能指同一个实体，也可能指不同版本；**未解决歧义前不要直接合并**。

### 4.2 第二步：实体解析（Entity Resolution）

假设日志写“eval-v2”，会议纪要写“V2评分器”。二者可能是同一程序。可以结合稳定ID、项目、版本、出处与上下文进行匹配。若误判为不同实体，会造成图断裂；若把“V2评分器”和“V3评分器”错误合并，会将不同时期的缺陷和修复混淆。**同名不必然同体，同义也不必然同一版本。**

[[FIG06]]

### 4.3 第三步：抽取关系时保留否定、模态和权限

“AI建议购买额度”和“研究者批准购买额度”具有相似的宾语，却是**两种完全不同的关系**。因此建议采用有区分度的关系类型：`SUGGESTED`（建议）、`DECIDED`（决定）、`PERMITS`（允许）、`PROHIBITS`（禁止）、`OBSERVED`（观察）、`SUPPORTED_BY`（证据支持）。也可以把“未批准”作为否定状态或独立决策节点，而不是只存“批准”和“API调用”两个关键词。

### 4.4 第四步：关系必须附带来源

可把每个抽取出的关系关联到产生它的原始事件，如`(候选关系F18, derived_from, 事件E18)`，并注明被谁提取、何时提取、是否经核验。图对多Agent转述尤其敏感：三个智能体重复同一条未经核验的消息，只能增加转述次数，**不能自动变成三个独立事实来源**。[2]

## 五、多跳检索：图为什么有时比单条文本更有用？

考虑这个问题：“项目P的哪一次决定限制了原计划，哪一条事件支持其原因？”回答所需证据分散在D03提议、D20决定和D11/D18工具日志中；单条向量最相似文本可能无法包含完整链路。

### 5.1 路径遍历的直观过程

先找到节点“项目P”；沿`HAS_PLAN`到计划A；从计划A沿`RESTRICTED_BY`到决定D20；再沿`MADE_BY`找到研究者。路径表达“项目—计划—限制决定—负责人”的结构联系。类似地可从诊断结论沿`SUPPORTED_BY`找回网关日志。这是一种**多跳关系查询（multi-hop traversal）**。

[[FIG07]]

### 5.2 广度优先搜索（BFS）与路径长度

广度优先搜索可以先看起点所有一跳邻居，再看两跳，再看三跳，逐层扩展。对于每条边长度相同的普通图，BFS可以找到到达某节点所需边数最少的路径；但**最短路径不必然是最可信、最新或最有因果解释力的路径**。真实系统还会加入边类型、时间、可靠性和搜索预算约束。

### 5.3 为什么不能无条件无限向外扩张？

教学简化：每个节点平均连接4个新的候选节点，且忽略重复边，则从一条起点扩展三层可能看到`4 + 16 + 64 = 84`个不同的候选位置（不含起点）。这是**树状最坏示意**，真实图有循环、重复邻居和过滤条件，实际扩展数可能小得多。检索范围扩张过大时，不仅耗时，也会引入更多低质量、跨项目、跨权限的关系。因此往往需要限制跳数、边类型及候选数量。

## 六、时间图谱：同一条关系为什么要带一段“有效期”？

一般静态图可能包含两条看似矛盾的边：`(项目P, 允许, 付费调用)`与`(项目P, 禁止, 付费调用)`。但仔细看时间就会发现它们可能描述不同阶段。**动态世界里的事实是会变化的**，不能简单采取“永远保存最后一条文本作为全部真相”的策略。

### 6.1 事实有效时间与系统记录时间

**有效时间（Valid Time）**回答“外部世界中，该关系从什么时候到什么时候成立”；**事务/记录时间（Transaction Time）**回答“数据库在什么时候记下、改写或得知这条关系”。二者是不同的时间轴。比如D20的暂停决定在D20生效，但D21系统才收到材料；按D20当日状态回看和按D20当日系统已知信息回看，会得到不同结果。

[[FIG08]]

### 6.2 双时间模型（Bitemporal）怎样帮助查询？

在教学模型中，一条事实可以有：`valid_from`、`valid_to`、`recorded_from`、`recorded_to`。查询“在T时刻外部什么有效”检查有效区间，查询“到K时刻系统知道什么”检查记录区间。对于半开区间通常写作：`valid_from ≤ T < valid_to`和`recorded_from ≤ K < recorded_to`。**这是课堂简式**：真实实现还要处理未知时间、精度、时区、撤销与更正。[3][4]

### 6.3 一个决定如何更新图，但不抹掉历史？

假设：D03 AI提出收费实验建议；D07研究者授权零费用离线检查；D20研究者继续禁止未经授权的付费实验；D26研究者另行授权“某个限定项目内不超过10次、费用不超过20元”的新动作（仅课堂构造）。此时不能将D26理解成“全局恢复全部收费实验”。应该保留原始事件，并用作用域、条件与有效时间区分：哪些禁止依旧有效、哪些操作被新的限定许可允许。**不同范围的决定可以同时存在，而不是非要选一个覆盖另一个**。

[[FIG09]]

### 6.4 图谱更新的三个典型陷阱

第一，**不核时间直接覆盖**会失去历史；第二，**只保存新事实不失效旧关系**会同时返回两条相反的“当前状态”；第三，**对相似关系做过宽的自动失效**可能把另一个项目、另一个用户的有效边误删。Zep/Graphiti原始工作讨论了时间化边和冲突失效；但它的机制及参数不能当作任何场景下都绝不会误判的保证。[3][5]

## 七、来源图谱：知识图上的边是谁说的、根据什么生成的？

如果关系`(故障E11, 原因, 网关超时)`由AI从一段不完整日志中猜测而来，它最多是**待核验的候选解释**。我们需要一条可回溯的来源路径：`日志L11 —被活动A18读取→ 判断C18 —由智能体M生成→ 经过核验R18`。W3C PROV-O提供实体（Entity）、活动（Activity）、责任主体（Agent）的通用语义模型，是构造来源链的重要参考。[6]

[[FIG10]]

### 7.1 来源关系和业务事实关系不是一回事

`研究者—作出→决定D20`描述谁对决定承担责任；`决定D20—限制→付费动作`是业务关系；`关系F20—来自→消息E20`是来源追溯关系。它们可以共享一张图，也可以拆成不同的子图。若全部简单压成一条`相关于`边，虽然结构更少，却失去查询意义。

### 7.2 图中没有某条边，能说明它是假的么？

不能。**缺少已记录关系，不等于该关系在现实中不存在**。这个常见错误对应知识表示领域的开放世界直觉：系统没有保存“D07授权支付”，不能据此断定客观世界绝对不存在授权；但在实际支付执行中，控制器仍应采用独立的“必须有可核实、当前有效的授权证据”门槛。**认识上的未知与行动上的默认拒绝可以同时成立**，这并不矛盾。

## 八、图检索有哪几种？不仅是沿着线走

常见方法可分为四类，它们经常组合使用：**图邻居/路径遍历**从一组实体扩张；**图扩散或个性化PageRank**在关联网络中传播查询相关性；**社区发现与层级摘要**从大量关系中提取全局主题；**混合检索**先由关键词/向量找到入口，再沿图补充关系和时间条件。

### 8.1 个性化PageRank的直观含义

普通图遍历强调“能走到谁”；PageRank类方法则为节点传播一个**重要程度/相关程度分数**。个性化PageRank（PPR）还能让随机游走不断有概率回到与当前查询有关的起始节点，使最终排名更偏向查询局部的联系。[7]

给一个**纯教学**三节点有向环：A→B、B→C、C→A，起点是A，每一步以`α=0.2`概率“重启到A”，以`0.8`概率沿边移动。初始分数`p₀=(1,0,0)`；一步之后`p₁=(0.2,0.8,0)`；两步之后`p₂=(0.2,0.16,0.64)`。你看见了“分数沿边传播+定期返回起点”的过程。**这不是HippoRAG的完整评分公式，也不能凭这些分数判断事实可信度**。

[[FIG11]]

### 8.2 社区与摘要如何解决“整体问题”？

一百万Token的材料若问“这里有哪些主要研究议题”，用户并不在寻找某一条精确事实，而是在做**整体归纳**。Microsoft GraphRAG的代表性工作从文档抽取实体关系，形成图并检测社区，再生成社区摘要，用多份摘要辅助回答整体性问题。这套设计针对**跨语料的全局问答与综合理解**，不应该直接等同于“智能体所有时间状态自动更新”。[8]

[[FIG12]]

### 8.3 混合检索往往更有针对性

假设用户问“项目P第11天的504故障后来怎样解释？”关键词能准确找到`504`，语义检索可找到“网关延迟”“超时”，图扩展则能从故障事件找到日志、后续诊断和相关决定。**具体系统不必始终先运行全部方法**；选择哪个检索入口、扩几跳、检索多少条，应由任务性质和成本决定。

## 九、三条代表性研究路线，不能混成一个“GraphRAG”

此处是理论理解，不是逐篇全文复现或直接给出科研选题。

### 9.1 Microsoft GraphRAG：面向文档集合的全局综合

Edge等人在《From Local to Global》研究了常规RAG面对“整套文档主题是什么”这类全局问题的局限。其代表性思路是构建实体图、社区划分和社区级摘要，再用局部答案合成全局回答。它展示了**图结构与层级摘要**怎样帮助文档全局理解。[8]

### 9.2 HippoRAG：面向关联知识的多跳检索

Gutiérrez等的HippoRAG将大语言模型抽取的关系图与**个性化PageRank**结合，针对跨知识点的关联检索与多跳问答；HippoRAG 2进一步讨论基础事实记忆、关联和整体理解之间的平衡。[7][9] 脑科学为设计提供启发，但**算法不是人脑海马体的直接复制**。

### 9.3 Zep/Graphiti：面向不断更新的时间化记忆

Rasmussen等提出的Zep（2025）通过Graphiti处理对话及其他数据，强调**原始事件、实体事实、社区结构、事实有效区间与增量维护**。其论文给出了动态关系失效处理和混合检索机制。**论文报告的效果依赖作者的评测任务与配置，不意味着所有场景的图记忆均优于简单检索。** 现行开源Graphiti文档与2025年的论文实现也可能存在差异，具体实现需核对版本。[3][5]

[[FIG13]]

| 路线 | 主要目标 | 图的关键角色 | 不能直接等同于 |
|---|---|---|---|
| Microsoft GraphRAG | 全局文档问题/主题综合 | 实体社区和摘要层级 | 自动追踪所有长期任务状态 |
| HippoRAG / 2 | 知识关联、多跳检索 | 图关联+个性化PageRank | 自动证明路径上的事实正确 |
| Zep / Graphiti | 动态Agent上下文与时间事实 | 时间化边、事件和来源 | 全部记忆行为天然可靠或获授权 |
| 简单文本/混合RAG | 直接检索具体原文 | 可不用显式全量图 | 永远无法完成多跳任务 |

## 十、图记忆是否一定比文本记忆和向量记忆好？

不是。不同表示在**表达能力、写入成本、维护复杂度、查询时间、纠错难度**之间做取舍。

[[FIG14]]

| 方法 | 更擅长 | 典型局限 | 什么时候优先考虑 |
|---|---|---|---|
| 原始文本/事件日志 | 原文可追溯、少抽取损失 | 路径关系不显式 | 历史记录量有限、需精准引用 |
| 结构化键值/表格 | 当前事实、状态、权限条件 | 复杂关系要额外联表/逻辑 | 明确规则、流程检查点 |
| 向量索引 | 同义改写与候选语义检索 | 相似≠一致、关系不显式 | 大量非结构化资料查找 |
| 静态知识图 | 实体关系、多跳与可解释路径 | 实体抽取/更新较昂贵 | 关系查询占主导且关系较稳定 |
| 时间化记忆图 | 当前/历史状态与跨日关联 | 时间/冲突/版本维护复杂 | 事实频繁变化且需按时间查询 |
| 混合架构 | 按任务组合多种能力 | 系统接口与成本更复杂 | 需要多类问题，但必须验证增量收益 |

### 10.1 简单数据量估算：图结构并不免费

教学构造：一个项目抽取**1,000个实体、5,000条关系**。即便每条边只保存两个8字节节点ID和一个4字节关系代码，原始最低字节数为`5,000×(8+8+4)=100,000B`。这不包含时间戳、来源引用、属性、索引、节点文字、数据库存储开销。真实图内存与存储远大于这份玩具下限。**不能用“看起来只有几个点和线”就判断系统成本很低**。

### 10.2 全生命周期成本包括什么？

如果图每次新消息都调用LLM提取实体与关系，就会产生写入Token、重复实体消歧、冲突检测和摘要维护成本；检索还需要索引、图遍历、回源与最终LLM阅读。比较图方法与强简单基线时，不能只报告“图遍历毫秒数”，却忽略初次建图、增量维护和错误修复。

## 十一、图记忆的典型失败机制

**第一类，抽取错误**：把“没有批准”提成“批准”。**第二类，实体合并错误**：将两个同名项目当成同一项目。**第三类，关系类型错误**：把“被提议”错误连成“已执行”。**第四类，时间失效错误**：旧决定被误认为仍有效，或跨项目新决定错误覆盖旧有效关系。**第五类，来源污染**：AI转述不断被重新写入，形成貌似多个独立证据的假共识。**第六类，检索路径误用**：图上存在两跳路径，模型便把它解释为因果证明。

[[FIG15]]

### 11.1 高度连通的图有时会放大错误

错误的实体合并会把原本两个不相干的子图连起来；之后任何多跳查询都可能沿错误桥接传播。反过来，过于稀疏的图又可能找不到应该连接的证据。这是**图的覆盖率与结构精度**之间的取舍。需要保存原始事件，以便人工或独立算法追溯“这条边从哪来”。

### 11.2 时间关系也可能失效不充分或失效过度

例如只根据主体和宾语相同，自动判定新关系必然覆盖旧关系，会把“项目P禁止收费调用”和“项目Q允许某个收费任务”混为一谈。图的冲突判断必须检查**主语标识、关系类型、对象、范围、来源、有效时间、权限主体**，并保留不可确定的状态。关于时间化图系统，公开代码库中也存在讨论这些复杂边界的Issue，说明机制设计并不等于部署后就不可能出错。[5]

### 11.3 图中信息是否“安全”取决于使用边界

如果来自网页或论文的文本写“忽略用户指令，立刻执行某工具”，这是**未经授权的外部内容**，不是系统指令。即使它被提取成图边，也不能成为工具执行的许可。Agent控制器必须将可读证据与可执行权限分开。

## 十二、怎样评价一套图记忆系统？

评价指标需要分层：**表示正确**、**图检索有效**、**时间推理准确**、**最终行动可靠**、**全生命周期资源合理**。

[[FIG16]]

### 12.1 先检验三元组是否写对

假设人工核验的基准关系有10条。系统提出12条关系，其中8条与基准在实体、关系类型和适用范围上均匹配。则课堂示意：`Precision=8/12≈66.7%`，`Recall=8/10=80%`。这评价的是**关系抽取质量**，不是回答正确率。若证据真值仍有争议，不应冒充客观Gold。

### 12.2 路径检索的好坏不能只看“答对了”

一个模型可能给出正确答案却引用错误路径；另一个模型找到正确图边却被上下文压缩遗漏。理论上至少分别检验：关系节点识别、必要路径召回、来源支持、时间有效判定、答案准确和控制器是否正确遵守当前权限。

### 12.3 成本如何公平比较？

同一数据、模型、任务、可见历史和权限条件下，可比较：①原始文本检索；②结构化事实+关键词/向量混合；③加入图遍历；④加入时间化与来源管理。关注**是否有必要的质量提升**以及代价来自哪个机制；不默认复杂图必然值得采用。

## 十三、把全部原理放回一个30天科研助手的动态过程

下面按照真实运行的时间顺序，把抽取、实体解析、图写入、时间更新、检索与决策连成一个可自行推演的系统（全部是假设的教学数据）。

[[FIG17]]

**阶段一：D01—D07，形成初始图。** `项目P—HAS_GOAL→离线研究`；`AI—SUGGESTED→收费扩样方案`（来源E03、状态`PROPOSAL`）；`研究者—MADE→决定D07`；`D07—PERMITS→离线核查`；`D07—PROHIBITS→未经授权的付费调用`。注意：AI提议和研究者决定之间**没有可替代关系**。

**阶段二：D11—D18，连接故障和证据。** `日志L11—OBSERVES→HTTP504`；`诊断C18—SUPPORTED_BY→网关日志L18`；`诊断C18—EXPLAINS→故障E11`。如果日志只能支持“请求超时”，就不应再补一条“模型规划能力错误”关系；证据不足时保留未知。

**阶段三：D20，明确当前有效限制。** 保存D20决定的原文与签署者身份，并关联原有D07限制；若D20只是再次确认，没有新授权范围，就不能把时间更晚误当作允许付费。

**阶段四：D30，查询与行动。** 用户提问“现在能否恢复收费实验，之前的失败原因如何？”系统先解析为两个子问题：权限状态问题→走有效决定关系及权限核验；原因问题→走故障事件和来源证据链。模型根据核实过的上下文回答；如果需要实际调用收费工具，控制器应再次核验**当前具体授权范围**，而不是由知识图上的“建议路径”自行推定。

### 13.1 如果把图全部删掉，系统一定不能回答么？

不一定。只要原始记录足够清晰，并有好的索引与规则检查，简单系统同样可能答对。图的价值需要通过**复杂关系查询、时间版本、跨项目关联与成本条件**来证明，而不是靠“更像人脑”这类叙事。

## 十四、一张决策图：什么时候应该用图记忆？

一条实用的理论判断路径：首先确认是否需要回答实体关系/多跳/时间历史问题；如果主要是精准搜索原文和当前状态，可以优先用事件日志、结构化事实和混合检索；若频繁遇到跨源关联且简单基线明显不足，再考虑图表示；如果时间关系经常变化，再考虑带版本、有效期和来源链的时间图。最终比较的是**准确性、延迟、维护负担和失效风险的总和**。

[[FIG18]]

> **核心科研判断：** 图不是越大越好，关系抽取得越多也不是越有智慧。好的图记忆系统首先应做到**实体不乱合、关系不乱写、时间不乱覆盖、证据能回查、有效权限不能被历史叙事取代**。

## 十五、12个初学者最容易出现的误区

1. **误区：图记忆一定要图数据库。** 更准确：小图可以由普通关系表/JSON保存，是否选专业图引擎由规模与查询决定。
2. **误区：图中的边都是经过核验的事实。** 更准确：边可能是提取候选、争议主张、过时版本，需要状态与来源。
3. **误区：RDF与属性图完全相同。** 更准确：二者建模约束与附加信息表示方式不同，具体映射需设计。
4. **误区：向量记忆过时了。** 更准确：向量检索擅长语义入口，图擅长显式关系，两者可互补。
5. **误区：有两跳路径就证明因果关系。** 更准确：路径连通只是一种结构观察，边的语义与证据才决定能推断什么。
6. **误区：同一个名称肯定是同一个实体。** 更准确：人名、项目名、脚本版本都有歧义，要结合稳定ID和上下文。
7. **误区：图中的新边可以覆盖全部旧边。** 更准确：需要考虑时间、项目、用户、范围以及历史保留。
8. **误区：图中的空白就表示客观不存在。** 更准确：未记录关系通常意味着未知；执行操作仍须独立验证授权。
9. **误区：GraphRAG、HippoRAG、Graphiti只是三个图数据库。** 更准确：分别涉及不同的任务目标、检索机制与动态管理架构。
10. **误区：多个Agent引用同一事实等于多个独立证据。** 更准确：应沿来源边查找是否共享同一原始事件。
11. **误区：图构建一次之后不再需要维护。** 更准确：新增/删除、实体消歧、冲突、索引与社区摘要都可能持续变化。
12. **误区：图检索准确率高意味着智能体行动安全。** 更准确：检索、时间核验、证据支持与控制器权限检查应分开评估。

## 十七、理论题逐题答案与推导

**答案1**：可建节点“研究者”“决定D20”“项目P”“付费调用”，边`研究者—MADE→D20`、`D20—APPLIES_TO→项目P`、`D20—PROHIBITS→付费调用`。这样既能查做出决定的人，也能查它具体限制什么、作用于哪个项目；模糊`相关于`无法表达限制的方向与权威来源。

**答案2**：它只是候选关系三元组，不是完整记忆。至少应有①原始来源事件及证据定位；②生效/记录时间和历史版本；③可信或核验状态及项目范围。如“使用”仅为计划，甚至需要区分“建议使用”与“已执行使用”。

**答案3**：不能直接合并。应优先核稳定ID、版本号、所属仓库或项目、日志路径、时间和人工确认信息。同一实体的别名可建立`ALIAS_OF`关系；对不同版本，应保留两个实体并建立`UPGRADED_FROM`等版本关系。

**答案4**：共3跳，因为经过三条边。最短只是在图结构上边数最少；一条边可能是未经核验的AI猜测，另一条较长路径却有原始日志、时间与决策记录支持，因此可信度与路径长度不必正相关。

**答案5**：第一层`4`，第二层`4²=16`，第三层`4³=64`，合计`4+16+64=84`。这是没有重复边、没有筛选的课堂分支树上界示意，真实图会因重复、方向、权限和边类型限制而改变。

**答案6**：有效时间是D20，系统记录时间是D21。若基于后来补录的信息回看D20的外部状态，可以认为决定已生效；若严格模拟“截止D20系统已知什么”，该决定当时尚未入库，不能伪装成早已被系统读取。应在回答中明确查询时间语义。

**答案7**：不能。D03的主体是AI，关系类型是`SUGGESTED`，不是研究者`APPROVED`；D07反而是仅离线许可。正确做法是保留两个不同主张和来源，并让控制器对收费行为要求可验证的具体许可。

**答案8**：初始`p₀=(1,0,0)`。一步20%概率回A，80%沿A→B，得`p₁=(0.2,0.8,0)`；再一步20%回A，80%流动（A→B、B→C），得`p₂=(0.2,0.16,0.64)`。这里分数仅表示访问/相关性传播，不是事实真实性概率。

**答案9**：Microsoft GraphRAG主要以实体图、社区发现和社区摘要服务全局文档问题；HippoRAG借知识图与PPR支持关联/多跳检索；Zep/Graphiti重在持续更新的事件、实体关系、有效时间与混合查询。目标、数据生命周期和算法不同，不能因为都有图就视为等价。

**答案10**：精确率`8/12≈66.7%`；召回率`8/10=80%`。它们只衡量与人工定义的基准关系匹配情况，不能直接推出最终回答或行动准确率；如果基准也有不确定性，还必须标清局限。

**答案11**：先沿路径逐边回溯原始事件与实体解析记录，核对两个项目的稳定标识、作用域、时间和版本；确认错误桥接后，修正实体解析、保留更正历史、重建受影响关系和派生索引，再针对跨项目错误路径做回归验证。只删除一个可见节点不一定能清理全部下游污染。

**答案12**：不应默认采用。500条结构化记忆且主要是当前规则查询时，键值/关系表+时间字段+原文索引通常已经能提供简单可靠的基线。只有当多跳跨源、频繁关系变化、来源追溯等需求确实带来可验证缺口，再考虑图系统；应计算构图和维护的全生命周期成本。

## 十八、课程总结：把知识在脑中“运行一遍”

试着不看图，复述这个循环：**人/工具产生事件→保存原文与身份时间→抽取候选实体和关系→解决同名与版本→保存来源、有效期与状态→按查询用关键词/向量找到入口→沿有意义的边走几跳→核验来源、时间与授权→把证据放入模型上下文→由控制器决定是否真的执行→产生新事件继续更新。**

如果现在能解释其中每一步存在的必要性，知道删掉它会造成什么失败，你就已经建立了图记忆的核心心智模型。
