## 为什么一般的静态RAG不够

**第一部分 / 动机**

假设科研助手读到三次项目状态变化。普通向量库可能都能找到这些记录，但仅按语义相似度排序，会把早先的信息放在当前有效决定前面。

[图2：从语义相关到时间与来源约束：请在PDF对应页查看原始矢量图和箭头关系。]

D08： “项目P正在进行中。” D20： “P暂停。” D25： “P的一项子任务恢复离线工作。” 三句话都包含P、状态，却并非互相简单覆盖。

普通文档检索擅长寻找相关文本，但要回答“D18时P处于什么状态？”和“现在P是否允许收费？”需要额外的时间、范围与授权语义。 只靠近似向量并不能完成所有判定。

2025年Zep论文提出，把持续发生的会话和结构化业务数据处理成会随事件增量改变的时间化知识图谱；Graphiti是实现这些图操作的核心。论文强调动态关系与历史有效期。

**别过度归纳：**  这并不意味着“所有RAG都是静态的”，或“所有静态方法都比Graphiti差”。静态索引可以结合更新机制；关键是系统如何维护事实的有效状态和历史。


## 先复习：实体、关系、三元组

**第二部分 / 图的底层**

知识图谱不是一张“漂亮的关系图片”，它是一套能检索、更新和推理的结构化记忆表示。先用最简单的语句建立图模型。

[图3：实体、关系与时间状态的教学三元组：请在PDF对应页查看原始矢量图和箭头关系。]

“项目P由团队A负责”可以拆为 （项目P，负责方，团队A） 。其中项目P和团队A是实体，负责方是关系类型。图中事实通常挂在有向边上。

但“P于D20暂停”不仅说明两个实体之间有关联，还说明状态事实只在某个时间段有效，可能有原始会议纪要作为来源。

同一个词也可能指不同对象。例如“P”可能是项目名，也可能是实验策略代号。若实体消歧失败，后续图遍历会把无关记录错误串联起来。

**通俗类比：**  一般图谱像人物关系表；时间图谱像一部记录“谁与谁在何时形成什么关系，又在何时改变”的可查历史簿。


## 2025年论文：Zep与Graphiti谁负责什么

**第二部分 / 系统边界**

Zep是面向智能体的记忆/上下文服务；Graphiti则是构建与查询时间知识图谱的引擎。二者是平台与核心组件的关系，不能把两个名称当作同一类实体。

[图4：Zep、Graphiti、存储后端与使用者的边界：请在PDF对应页查看原始矢量图和箭头关系。]

在2025年的原论文中： Zep接收消息和结构化数据，Graphiti抽取实体关系并维护时间状态；随后Zep检索图中的相关事实并把它们组装为模型输入上下文。

在2026年官方文档中： Graphiti是开源时间知识图谱框架，Zep进一步提供托管上下文层、治理和部署选项。当前文档可能展示v4 API、新的图后端和产品功能，不应倒推到论文提交时。

| 层次 | 主要责任 | 不能自动推出 |
|---|---|---|
| Zep服务 | 接入、管理、检索、交付上下文 | 不是基础模型本身 |
| Graphiti核心 | 实体/关系/时间处理与图检索 | 不是独立的许可裁决器 |
| 图数据库后端 | 持久化节点、边与索引 | 不是事实真实性证明 |
| 使用它的智能体 | 规划、推理、调用工具 | 不能把建议冒称执行回执 |

**证据来源：**  原论文arXiv:2501.13956（2025-01-20）§2–4；Graphiti当前v4官方Overview与Zep新版Context Graph文档（检索截至2026-10-19）。


## Zep论文的“三层图”究竟是什么

**第二部分 / 三层结构**

这是原论文最重要的结构设计之一：Zep不是只保存“实体之间的连接”，还保留产生这些知识的事件，并用社区层组织更抽象的主题。

[图5：Zep 2025原论文的事件、实体、社区三层知识图谱：请在PDF对应页查看原始矢量图和箭头关系。]

1. Episode Subgraph（事件层）： 每条输入消息、文本或JSON作为原始事件节点，可保留说话人、引用时间等信息。这层是派生事实回溯的基础。
2. Semantic Entity Subgraph（语义实体层）： 从事件中抽取实体、消歧、建立含事实的关系边；新的边可能使旧边失效。
3. Community Subgraph（社区层）： 把联系密集的实体分组，并为群组生成主题摘要。便于高层概览，但摘要也可能损失细节。

三层不是按“低级/高级数据库产品”划分，也不一定对应三套独立物理数据库。它们是逻辑子图，对应 来源、可查询事实、全局主题 三个视角。

**原论文边界：**  2025论文明确描述三个层级；2026年Graphiti v4公开文档扩展了Node/Edge类型，不能把新版所有类名都当作2025论文已有。


## Episode：写入从“原始事件”开始

**第二部分 / 事件录入**

一条原始输入为什么要单独留下？因为后续实体提取和摘要可以出错，只有保留对应来源，才能把派生主张追回原始话语。

[图6：从一次Episode到可追踪的候选事实：请在PDF对应页查看原始矢量图和箭头关系。]

以D20的对话为例：“从今天开始暂停项目P的付费调用。”可以作为一个会话事件进入图，附上发言者、发生时间、事件唯一标识和所属项目。

Graphiti官方文档将一次录入称为 Episode ，主要支持 text、message、json 。`reference_time`用来解析“明天”“两周前”等相对时间。

同一事件可产生多条事实。例如P、付费API、暂停动作、D20生效时间。来源事件与派生事实之间应有引用关系。

**记忆链中的重要边界：**  事件“用户这样说过”与主张“用户说的内容一定真实”不同。保留原文证明记录有出处，不保证声明本身准确，更不替代身份鉴权。


## 为什么实体消歧比抽出词语更难

**第三部分 / 增量构图**

LLM找到“项目P”四个字很容易，但决定它与数据库里哪一个“P”节点相同，需要结合项目作用域、来源与上下文。

[图7：实体抽取、候选召回与消歧的动态过程：请在PDF对应页查看原始矢量图和箭头关系。]

2025论文描述：先利用当前消息及最近若干消息提取实体，得到名称与概览摘要；然后结合 向量近邻与全文搜索 寻找候选旧实体，最后用LLM进行Entity Resolution（实体消歧）。

如果最新一轮只说“它昨天停了”，需要上一轮的“项目P”才能确定“它”指谁；如果另一个项目也简称P，则不能仅凭同名合并。

原论文具体实现中使用最近4条消息提供上下文，利用1024维实体名称向量做近邻匹配，随后使用受控Cypher查询写入。这些是 2025年论文实验设置 ，不是永远不变的API协议。

**一个失败如何传播：**  把项目P与策略P合并，最初只是实体错误；之后“暂停付费”可能沿着图关联到错误项目，再被检索出来影响行动。实体消歧是可靠性的前端关口。


## 关系边是事实，不只是连接线

**第三部分 / 事实抽取**

把“P从D20起暂停新增收费调用”存入时间图谱，核心不是画一根P到API的线，而是保存清楚这根边代表什么、适用于谁、何时有效。

[图8：带时间、来源与动作含义的实体关系边：请在PDF对应页查看原始矢量图和箭头关系。]

| 字段 | 教学示意 | 为什么需要 |
|---|---|---|
| source / target | 项目P → 新增付费调用 | 确定事实对象 |
| relation / fact | 当前暂停 / 不得新增 | 区分允许与禁止 |
| valid_at | D20 | 何时生效 |
| invalid_at | 暂未设置 | 何时不再有效 |
| created_at | D22 | 系统何时获知 |
| provenance | 事件E20 | 能够追溯原话 |

Graphiti把事实嵌入向量以支持语义检索，同时用既有实体对约束候选相似边，降低不相关旧事实错误合并的概率。新边加入以后，系统还需分析是否与旧边在时间上冲突。

**重要限定：**  这里的字段是为了教学直观呈现的逻辑卡片；具体API字段名、可空性与存储实现要以所读Graphiti版本为准。


## 双时间：一个事实竟然需要两套时钟

**第三部分 / 核心原理**

这部分是整讲最重要的知识。系统有时在某天才知道一个早已生效的状态，如果只存一个日期，就不能同时回答“当时世界怎样”和“当时系统知道什么”。

[图9：事实有效时间与系统获知时间的两条独立时间轴：请在PDF对应页查看原始矢量图和箭头关系。]

有效时间（Valid time）： 关系在被描述的世界里，从什么时候开始真实有效，到什么时候结束。例如P从D20起暂停。

事务/获知时间（Transaction time）： 数据库从什么时候记录这条事实，又从什么时候把它标记为失效。例如系统网络中断直到D22才收到了D20决定。

四个常见字段可以概括为：`valid_at`、`invalid_at`、`created_at`、`expired_at`。注意不同文档版本与应用采用的时区和命名可能有所变化。

**具体场景：**  在D21提问“P是否已暂停”，事后回看事实有效时间，答案可以是“已暂停”；但在D21问“系统当时是否已收到暂停消息”，事务时间答案可能是“还不知道”。


## 用不等式重建一个历史查询

**第三部分 / 时间推演**

不用微积分，只需要理解一个半开区间：包含起点，不包含终点。它解决连续状态变更时边界时刻如何归属的问题。

[图10：旧边设置失效时间，新边承接新的有效区间：请在PDF对应页查看原始矢量图和箭头关系。]

若旧状态在D12生效，在D20失效：`valid ∈ [D12, D20)`；新状态从D20起生效：`valid ∈ [D20, +∞)`。因此查询D19得到旧状态，查询D20得到新状态。

`valid_from ≤ t < valid_to 在查询时间 t 上，哪些边的有效期覆盖这一时刻？`

若系统到D22才得知新状态，那么D21的“当时系统认识”查询还要加上事务时间条件：`known_from ≤ k < known_to`。双时间检索是对两个时钟同时约束。

| 问题 | 要使用哪条时间轴 | 教学答案 |
|---|---|---|
| D19时P的任务状态？ | 有效时间 | 进行中 |
| 现在P任务状态？ | 有效时间 | 暂停 |
| D21系统当时知道什么？ | 事务时间 | 可能仍认为进行中 |
| D23回看D21发生了什么？ | 有效时间＋现在证据 | D20已暂停 |

**与权限的关系：**  任务状态=暂停/进行中与收费授权是两个独立字段或关系。即使D30任务恢复进行中，也不能推断自动获得付费权限。


## 新边出现时：旧关系怎样失效

**第三部分 / 冲突与更新**

Graphiti不只是不断追加新的关系，还要处理和旧事实存在时间重叠、语义矛盾的边。这个过程比“哪个更近就删除哪个”复杂。

[图11：新事实入图和旧边失效的完整步骤：请在PDF对应页查看原始矢量图和箭头关系。]

1. 新事件被抽取为候选事实边，如“P从D20起处于暂停状态”。
2. 先检索同一对象或相邻实体之间语义相关的旧边，如“P从D12起处于进行中状态”。
3. 模型辅助判断两条关系是否真的冲突、是否作用于同一主体与条件。
4. 若旧事实被新状态替代，设置其失效日期，当前视图不再返回旧边；原始事件及历史关系仍可回溯。

2025论文明确写到以LLM比较相关旧边，遇到时间重叠的冲突时令旧边失效，通常让旧边`invalid_at`指向新边开始有效的时刻。**这是一种实现方案，不是事实判断永远正确的保证。**

**危险的反例：**  D12说“项目P暂停新增付费调用”，D26说“项目Q获一次付费许可”。词面上有“暂停/许可”冲突，但主语不同，不能让Q许可使P限制失效。


## 来源追溯：图谱凭什么认为一条边存在

**第三部分 / 原始证据**

图中的一句话可能经历“原话→实体抽取→关系抽取→冲突判断→摘要→搜索”多次处理。最后检索到的边应当还能追溯到底是谁、在什么材料中说过。

[图12：Episode—提取活动—派生事实—最终查询之间的来源链：请在PDF对应页查看原始矢量图和箭头关系。]

2025年论文中，事件层与语义实体层之间建有引用连接，事实边可回溯到产生它的Episode。Graphiti当前文档也强调每个事件与它所提到的实体之间的`MENTIONS`关系。

从“D20正式暂停”派生出“P状态暂停”这条边，应能访问对应事件。若查询时只有一条LLM摘要，却没有消息ID、说话者与日期，那么虽然语义清晰，也可能发生来源漂移。

不同AI反复转述同一原话，不应该被当作多个彼此独立的确认；它们的根来源可能只有同一条Episode。

**来源≠真值：**  有来源可以回答“从哪里得到这项主张”，但来源的身份、真实性、适用范围及证据强度仍需另外核验。


## 社区层：为什么还要把很多实体聚成群

**第三部分 / 高层知识**

一张大型实体图可能包含几万个实体。如果智能体问“整个研究项目主要存在哪几类问题”，逐条读取局部关系既昂贵又缺乏概览。

[图13：从局部实体关系构建更高层的社区概览：请在PDF对应页查看原始矢量图和箭头关系。]

2025年Zep论文引入社区子图：按照连接结构将实体分到关系密集的群组，给群组生成名称和摘要。这样既能读取某个具体实体，也能定位主题群组的高级描述。

论文采用**Label Propagation（标签传播）**识别社区，并描述了新节点加入时的增量分配：查看邻居社区标签，加入邻居较多的群组，然后更新摘要。

增量更新并不总与“从零重跑全部社区检测”相同。论文指出长期增量可能发生漂移，因此仍需要周期性刷新。这是一个有价值的系统层权衡。

**通俗比喻：**  如果每张便签是“某一次API错误”，社区摘要就是“项目P的工具故障诊断档案”。它节省阅读时间，但摘要不能代替带来源的原始日志。


## 新消息源源不断到来：增量更新是否廉价

**第三部分 / 运行时成本**

“动态更新”并不等于“免费、立即、无风险”。每新增一个Episode，背后可能触发多次LLM、Embedding、去重、消歧、冲突判断和图数据库读写。

[图14：持续写入时的构图与索引维护路径：请在PDF对应页查看原始矢量图和箭头关系。]

为处理一条新消息，可能经历：实体提取、事实抽取、找旧实体、找旧关系、时间归一、矛盾判断、保存图、更新检索索引、维护社区。部分步骤可并发，部分需要顺序依赖。

图的增量修改可以比全图重建节约成本，但并不能消除维护成本。尤其是事件密集、实体歧义多、变更频繁的任务，旧边失效和社区摘要重算会不断发生。

如果一个实验只报告“检索延迟”，却不记录写入Token、构图时间、回滚和维护成本，就无法评价完整的长期记忆系统。

**比较时应注意：**  2025论文采用的LLM、Embedding、索引和计算环境，与2026新Graphiti可能完全不同。解释实验开销时必须锁定版本和可见调用。


## Zep 2025：记忆检索不是只查图邻居

**第四部分 / 混合检索**

有时用户记得原话中的独特缩写，有时只记得意思，有时必须跨几个实体沿关系找到历史。单一检索方式很难兼顾这些问题。

[图15：Zep论文Search—Rerank—Context三阶段记忆检索：请在PDF对应页查看原始矢量图和箭头关系。]

原论文列出三种召回： 向量余弦相似度 寻找语义相关事实， BM25全文检索 寻找关键字， BFS图遍历 扩展结构邻域。

候选结果之后，还可能使用RRF、MMR、节点距离或其他重排方法，最后由Context Constructor把事实及其有效日期、实体或社区摘要格式化为LLM可阅读的文本。

论文用公式表达整体路径：`f(α)=χ(ρ(φ(α)))`。无需记住希腊字母，只需理解`φ=搜索`、`ρ=重排`、`χ=生成上下文`。

**为什么这是“记忆检索”：**  并非图谱直接替代LLM推理，而是从长期图中挑选与当前问题有关的事实，以有限文字返回给模型。


## 一个问题为何要同时搜三路

**第四部分 / 候选生成**

假设用户问：“项目P曾因504故障暂停过哪些步骤，后来有什么证据？”不同检索渠道各自看到不同线索。

[图16：不同检索信号互补，但有不同失败入口：请在PDF对应页查看原始矢量图和箭头关系。]

| 检索路线 | 可能找到什么 | 可能遗漏什么 |
|---|---|---|
| BM25关键词 | 含“504”、专有日志ID的原话 | 同义表达的代理超时诊断 |
| 语义向量 | “网络故障”“代理超时”相关摘要 | 精确ID和否定状态 |
| 关系扩展BFS | D09故障→D18日志→诊断边 | 远处但关键的独立资料 |

Graphiti官方v4的便捷`search()`侧重向量+BM25并通过RRF融合；更丰富的`search_()`允许组合节点、边、事件、社区及其他排序方式。**不能把2025论文所有搜索步骤等同于2026默认API行为。**

对于当前授权等精确状态，检索后的强制核验仍应访问权威状态来源。哪怕图召回了正确边，也不能替代控制器的执行许可检查。

**科研阅读习惯：**  研究中的“Graph Retrieval”可能指真正沿边遍历，也可能指在图事实文本上做向量搜索。必须看方法和代码，而不是只看名称。


## 手算RRF：三个信号怎样融合排序

**第四部分 / 理论算例**

这里复习第08与22讲的RRF（Reciprocal Rank Fusion）。它是一个不依赖不同检索器原始分数尺度的排名融合方式，Zep与Graphiti均有相关实现。

[图17：三路检索融合的RRF教学手算：请在PDF对应页查看原始矢量图和箭头关系。]

教学设`k=10`，一条候选事实在关键词、向量、图邻域中的排名依次为r₁、r₂、r₃。每路得分为`1/(10+r)`，然后相加。

`RRF(d) = Σ 1 / (10 + rank_i(d)) 课堂例子使用k=10；这是演算参数，不代表Graphiti的默认配置`

| 候选 | 关键词r | 语义r | 图r | RRF得分 |
|---|---|---|---|---|
| A：P现行状态 | 1 | 3 | 2 | 1/11+1/13+1/12 = 0.25117 |
| B：旧AI建议 | 2 | 1 | 5 | 1/12+1/11+1/15 = 0.24091 |
| C：D09故障证据 | 4 | 2 | 1 | 1/14+1/12+1/11 = 0.24567 |

因此按RRF得到A ＞ C ＞ B。但即使B排第一，也无法证明B拥有权限；排名融合解决的只是 “值得先看哪些候选” 。

**容易误解：**  RRF不表示事实概率，不检查授权，也不保留完整的证据依赖链。完整证据选择仍需时间、来源和范围核验。


## 时间检索如何改变同一个问题的答案

**第四部分 / 历史查询**

很多“记忆错误”其实不是找不到过去的事实，而是把事实用于了错误日期、错误项目或者错误主体。

[图18：多日期记忆中存在“历史变化、当前状态与局部例外”：请在PDF对应页查看原始矢量图和箭头关系。]

问题一：“D15时项目P是否进行中？”要按有效时间回溯D15，而不是取最新边。问题二：“D30时项目P是否暂停？”要选D30有效的状态。

问题三：“D21系统当时知道P已经暂停了吗？”需要同时考察知识入库时间。如果正式决定D20生效，系统D22才录入，D21的内部认识仍可能落后。

问题四：“D30是否可以新增收费调用？”即便任务状态恢复，也要单独检查授权边。任务活动状态与费用审批属于不同关系类型。

**可独立推演的方法：**  每次读一条事实之前先问：“主体是谁？属性是什么？有效时间？系统什么时候得知？来源是谁？是否关乎执行授权？”


## 从检索候选到LLM真正看得见的上下文

**第四部分 / 记忆利用**

图数据库返回的可能是节点、边、时间字段和索引ID；LLM不会自动访问整个图。系统必须把一小组证据转换成可阅读文本。

[图19：从结构化图事实到LLM可见证据，再到真实行动：请在PDF对应页查看原始矢量图和箭头关系。]

2025论文的Context Constructor将相关事实及有效时间、实体名与摘要、社区描述拼成文字上下文，再交给LLM。这个过程是 数据到上下文的构造 ，不是模型权重记忆。

如果只将“P由团队A负责”放入输入，却没有“P已暂停”这条关系，模型仍可能无法正确回答授权问题。上下文长度充裕不意味着需要证据都已装入。

另一方面，过多的旧边可能挤占Token，并干扰模型对最新信息的使用。证据是否完整、是否适用以及排序和位置，都影响最终质量。

**系统责任链：**  写入正确→候选召回→时间来源核验→上下文选择→模型阅读→控制器行动，每一段都可能失败。第24讲已经解释了如何做分层归因。

## 2025原论文DMR成绩：优势究竟有多大

**第六部分 / 证据阅读**

第一次看论文时最容易被“比MemGPT好”吸引，但成熟的阅读方式是连同模型版本、其他基线和任务规模一起读完整的表格。

[图22：Zep 2025论文表1中的DMR对照（GPT-4-turbo）：请在PDF对应页查看原始矢量图和箭头关系。]

2025论文表1使用GPT-4-turbo比较：Zep 94.8% ，MemGPT（作者引用的已报道结果） 93.4% ，完整会话上下文基线 94.4% ，会话摘要 78.6% 。

Zep相对MemGPT仅高 1.4个百分点 ，相对完整会话基线仅高 0.4个百分点 。而原论文还指出，DMR每段对话最多约60条消息，通常能放进当代LLM的上下文，因此DMR不充分检验很长的连续历史。

论文另以gpt-4o-mini评测Zep 98.2% 、完整会话基线 98.0% 。不同底座模型数值不能直接混成一组“系统增益”。

**应学会的判断：**  作者数据支持“在指定DMR条件下表现很高”，但不能证明“图记忆一定优于完整历史回放”或“Graphiti能通用解决长期决策”。这是具体基准的证据边界。

## 什么时候时间图谱真的比简单记忆值得用

**第七部分 / 架构选择**

“可以使用图”与“必须使用图”是两回事。要从任务特性出发，比较可追溯性、时序变更、查询依赖和维护成本。

[图26：复杂图记忆与简单可维护状态记忆的取舍：请在PDF对应页查看原始矢量图和箭头关系。]

| 任务特征 | 可优先考虑 | 何时图结构更有价值 |
|---|---|---|
| 只需记住固定用户偏好 | 结构化键值或文本摘要 | 存在大量主体与冲突关系时 |
| 历史原文精准追溯 | 事件日志+全文检索 | 需要关联多主体来源路径时 |
| 大量近义回忆 | 向量+元数据 | 高相关实体关系跨跳时 |
| 频繁更新的多项目权限 | 权威状态表+事件日志 | 复杂作用域与历史关系查询时 |
| 跨部门长期业务变化 | 混合架构 | 时间图谱的复合查询与来源链可能值得成本 |

Zep/Graphiti可提供重要能力，但同样可能引入LLM抽取错误、实体合并失败、社区摘要漂移以及昂贵的写入/清理成本。简单的版本化事实表有时更稳健。

对于**直接决定是否调用付费API**这类关键动作，应将真实授权放在可强制校验的控制器/权限存储，不让图记忆的“推断关系”直接行使许可。

**科研价值判断：**  系统复杂度本身不是原创性。若图相对简单结构化状态能在可证伪问题中改善时序可靠性、证据追溯或质量—成本权衡，才值得深究。


## 系统怎样失败：最先出错的可能不是检索

**第七部分 / 可靠性分层**

观察到智能体最终误以为“项目P可以恢复收费”时，不能直接断言Graphiti检索失效。错误可能发生在多条不同的因果链上。

[图27：图记忆失效的六关因果诊断方法：请在PDF对应页查看原始矢量图和箭头关系。]

| 故障位置 | 典型错误 | 应当核查的对象 |
|---|---|---|
| 录入 | D20事件丢失或speaker错误 | 原始Episode与接收日志 |
| 实体消歧 | P项目与策略P合并 | 候选节点与归一关系 |
| 事实抽取 | 否定词/作用域被丢掉 | 新边对原句的支持 |
| 冲突失效 | 错误地将P限制标为过期 | 旧/新边的valid/invalid |
| 索引或缓存 | 权威库v20但索引仍v18 | 版本、刷新状态和延迟 |
| 查询与排序 | 旧AI建议被排在当前决定前 | 多路候选和reranker |
| LLM阅读 | 看见正确事实却理解错 | 实际可见输入与回答 |
| 控制执行 | 模型建议被直接当作批准 | 权限检查与真实工具回执 |

核心方法是把 真实原始事件→边与节点→候选搜索→阅读上下文→执行结果 逐段比对，保留不利证据，无法判定的分层标记未知。

**别把相关性当因果：**  例如多跳路径连通并不证明两个事件有因果关系；一次AI错误解释不能替代原始API、工具和网关日志。


## 完整成本不止一个查询延迟

**第七部分 / 资源估算**

为了理解长周期系统为什么要权衡，我们使用一组明确虚构的数字，不调用API，也不把它们误写成Zep实际价格。

[图28：端到端延迟分解与只报检索延迟的差别：请在PDF对应页查看原始矢量图和箭头关系。]

假设30天里每天50条Episode，共`30×50=1500`条。教学设每条新增事件需要平均3次LLM处理，每次1000输入Token和300输出Token。

`1500 × 3 × (1000 + 300) = 5,850,000 Token 此为写入处理Token总量的课堂估计，非Graphiti真实平均请求数`

若同时每日发生100次查询，30天又有3000次检索。应分别统计写入构图、Embedding和索引、查询、LLM阅读、错误更正与复审，不能只除以回答次数忽略积累成本。

另一个延迟例子：查询Embedding 70ms + 候选检索130ms + 回源核验45ms + 上下文打包25ms + LLM生成2000ms = 2270ms 。前四段仅270ms。若产品页只报检索p95，不等于整轮回答时间。

**研究中的必要分母：**  成本必须明确每条新事件、每次查询、每个独立任务或完整生命周期哪个是分母；错误传播和重做也可能显著增加总成本。


## 理论上怎样评价时间图谱的贡献

**第七部分 / 指标和控制**

好系统至少要答对，还应该知道如何找到证据，不能把已失效关系当成当前事实。把指标按机制拆开，有助于定位改进是否真实。

[图29：五层评价体系与因果定位：请在PDF对应页查看原始矢量图和箭头关系。]

- 实体层： 实体识别精确率、跨会话消歧正确率、错误合并率。
- 关系层： 三元组事实的出处支持率、边的时序有效性、冲突判断准确率。
- 检索层： Recall@K、完整证据链覆盖率、历史与当前查询分开计数。
- 利用层： 给定正确证据时的回答/决策质量与拒答合理性。
- 系统层： 任务成功、真实工具验证、写入/检索延迟和全生命周期费用。

如果一个方法使用更多LLM写入调用、更丰富的候选、更长提示，却只和非常弱的向量库比较，不能把所有性能差异都归给“时间图谱机制”。

公平理解应至少概念上考虑相同任务、模型、可见信息和预算，或明确声明比较的是整套产品协议而不是某个单一模块因果效应。

**纯理论阶段：**  本讲只学习评价原则和变量关系。正式研究需要另行设计实验，但现在不安排任何实际实验。

## 贯穿案例：第30天如何“正确回忆”

**第八部分 / 全案例**

第30天的提问是：“我们现在能否给项目P增加一次收费调用？”智能体如果真正理解时间图谱，应如何一步一步思考？

[图31：从动态记忆到可靠下一步行动的完整链路：请在PDF对应页查看原始矢量图和箭头关系。]

1. 明确问题主体： 项目P，不是Q。关注的是当前新增付费操作许可，而不是项目是否存在。
2. 构造检索： 查询P有关的权威决定、时间范围、有效状态以及对应原始Episode。
3. 多路召回： BM25找到“收费”“暂停”；向量找到“暂停新增调用”的同义记忆；图关系从P连接到当前状态及来源。
4. 回源核验： D04是AI建议，D12是研究者正式决定，D26是Q的局部许可；无证据显示P的暂停后来被撤销。
5. 生成结论： 目前不能据这些记录判断P新增收费已获授权，应指出D12限制仍有效并说明来源。
6. 控制器决策： 不执行有费用的工具调用；如需要变更范围，等待研究者新的明确决定。

这条流程展示时间图谱的价值所在：不是简单从历史句子中提取关键词，而是在来源、有效时间、范围和执行边界约束下组合证据。

**最终输出：**  “P仍按D12暂停新增付费。D26许可仅适用于Q，D04为AI建议。若要对P新增调用，需要新的明确授权。”（课堂预期回答）

## 理论题参考答案（1—4）

**第十一部分 / 完整答案**

参考答案不是标准句式模板，而是展示怎样由系统机制推导答案。

A1. Zep在2025论文中是智能体记忆服务，Graphiti是其时间知识图谱构建/查询引擎；2026文档的Zep是一套托管上下文层，开源Graphiti又有独立API和后端。图数据库负责实际存储节点/边；LLM负责生成文字候选与读上下文；使用LLM的Agent还需要独立控制器验证执行权限。不能把四者都称作“记忆模型”。

A2. 事件层保存D20原始消息、说话人、发生时间以及D22系统录入的来源信息；语义层可包含节点“项目P”“付费调用”和表示“暂停新增”的边，带D20有效期、D22记录时间、指向Episode的来源；社区层可能把该关系放入“项目P审批和资源管理”主题并维护摘要。社区摘要是派生概览，不是新的独立批准。

A3. 主体P与Q若混同会跨项目污染；否定词“暂停/不得”若丢失会反转事实；有效时间不明会错用旧决定；系统获知时间缺失无法回答历史知识状态；来源缺失无法定位发言者；效力/授权类别不明则可能将AI建议当作负责人决定。Embedding相似度无法补回这些丢失的结构字段。

A4. 如果消息真实且D20生效，则“D21实际世界状态”是已暂停；D21系统尚未收到D20消息，内部可能仍依据旧状态，这不是对实际状态的证明；D23回看D21应按有效时间说“D21已暂停”，同时可指出系统直到D22才获知。两条时间轴回答的问题不同。

**自测：**  对A4增加一个条件：若消息直到D23才经过核验，哪些答案需要改为“据后续证据认为”？这有助于区分时间信息与事实真实性。


## 理论题参考答案（5—8）

**第十一部分 / 完整答案**

这四题把半开区间、项目范围与检索排序转化为可复算的运算和决策步骤。

A5. D19满足D12 ≤ D19 ＜ D20，落入旧边；D20因为区间右侧不含D20，已不属于旧边，而属于从D20开始的新边；D30仍属于新边（假设没有后续状态变化）。半开区间避免一个边界时刻被两条互斥状态同时占有。

A6. 首先检查实体ID：P≠Q。还要检查“新增付费”和“一次例外许可”的关系类型，发言者是否有权、授权预算、有效时段、使用次数和来源。应同时保留P的暂停与Q的例外，不把两者误判成同主体状态冲突。

A7. A=1/11+1/13+1/12≈0.25117；B=1/12+1/11+1/15≈0.24091；C=1/14+1/12+1/11≈0.24567。因此A＞C＞B。RRF只融合候选名次，不验证事实、有效时间与许可。即使B第一，控制器也不应据此执行收费调用。

A8. Zep−MemGPT=94.8−93.4=1.4个百分点；Zep−全历史=94.8−94.4=0.4个百分点。支持“在作者的短DMR和指定GPT-4-turbo协议下表现略高”这一局部结论。不能由0.4个百分点断言图谱普遍优于全部可见历史，更不能声称降低了所有类型的错误。

**易错单位：**  百分点用于百分数的绝对差；百分比相对提升需要再除以基线。别把“94.8%高于94.4%”表述为“提高0.4%相对性能”。


## 理论题参考答案（9—12）

**第十一部分 / 完整答案**

后四题解释如何从一张论文表格走向可复查而不过度推断的科研结论。

A9. 绝对提升为71.2−60.2=11.0个百分点；相对提升是11.0/60.2≈18.27%。前者描述准确率差距，后者是相对基线的比例。在不同问题类型中提升并不一致，不能拿总体平均证明任何单一失败机制已解决。

A10. 不能。162ms是2026网页给出的 检索p95 ；2.58秒是2025论文中指定模型/流程的 端到端回答延迟 。不仅测量对象不同，模型版本、测试集、后端、索引和请求协议也不同。即使做除法得出某个数字，也没有因果或可比性意义。

A11. 三个Agent可能都沿同一网页及同一错误原句形成下游衍生，因此是同一个根来源的多个派生主张，并非三个独立证人。应记录每条事实来自哪个Episode、哪种摘要和中间转述，并保留根源依赖图；若找不到原始独立依据，应降低判断确定性。

A12. 先使用权威项目状态表与事件日志，确保主体ID、版本、有效时间、授权角色与费用限制均可独立强制核查；如果只有固定字段查询，这个简单方案可能更可靠。只有出现确实需要跨实体多跳、复杂历史解释、原始证据连接的任务，并证实简单方法在这些任务中失败，才加入时间图谱和混合索引；新增成本应包括抽取、消歧、更新、检索、维护和错误更正。

**最终判断：**  “时间图谱有用”是一项有边界的系统设计结论。它提供表达与检索能力，但不自动替代数据真实性、执行层权限、独立验收或科研实验的因果识别。


## 整讲独立重建：把每个环节放回动态循环

**第十二部分 / 完整知识图**

如果你能自己画出下面的因果流程，并用D01—D30案例说明每个箭头发生什么，说明已经掌握了本讲的核心机制。

[图35：第30讲可独立重建的完整心智模型：请在PDF对应页查看原始矢量图和箭头关系。]

1. 新消息首先成为附带说话人、时间和身份的Episode；这一步保存来源，不等于真值已核验。
2. 通过LLM抽取和实体消歧生成候选节点与事实边；把语义关系、项目范围和时间范围保存为结构化信息。
3. 若新事实与旧边真正在同一范围/时间发生冲突，则使旧边在对应时间之后失效；原始来源和旧历史保留。
4. 社区层可以组织高层摘要，但需要承认它可能漂移并增加成本。
5. 检索阶段组合向量、BM25和图关系信号，进行排名、时间与来源核验，再将少量证据装入当前LLM上下文。
6. 模型产出计划/回答建议；真实工具执行与费用许可仍需独立控制器核查；新结果再回到事件层。

三层知识图谱、双时间、增量维护与混合检索，共同构成Zep 2025论文的机制主线。真正的系统研究还必须比较基线、版本、证据有效性和生命周期成本。

**全讲最重要的一句话：**  时间图谱的价值，不在于把历史连得越密，而在于能回答“哪条关系在什么时候成立、根据什么证据、现在是否仍然适用”。
